# KONz 云备份：GitHub 方案细化

日期：2026-11-01（北京时间）。状态：研究记录；未修改地面站源码、未配置账号、未部署后端、未打包。

## 已确认的边界

- 保留软件投稿、电脑浏览器云端审核，未审核内容不进入软件公开列表。
- GitHub 保存完整内部 Flash HEX、每份投稿的两张实物照片；不裁剪原机设置。
- 使用独立轻量 Cloudflare Worker；R2 和 Access 不作为必须组件。管理员以指定 GitHub 账号登录。
- 已有网站、三条编译/更新 Worker 独立保留。云备份故障不妨碍本地离线备份。
- 软件不展示未批准/已下架条目；用户接受已经公开的 GitHub 直链仍可能访问。
- 审核通过的 HEX 与照片按原要求分别放在公开备份仓库的不同目录，由备份 ID 关联。

## 现有代码核对

app/desktop/dfu-backup.ts 中 DfuBackup.read 已按 DFU 内部 Flash 布局读两次，验证长度、逐字节一致，导出 Intel HEX；遇读保护不执行解锁或擦除。
当前 state.sha256 对原始 BIN 计算，不是 HEX 文本文件的哈希。新增服务需区分 imageSha256 与 hexFileSha256，下载核对后者，重复镜像识别使用前者和地址布局。
DfuBackupPanel.vue 现有功能仅扫描、读取保存和状态显示，尚无投稿业务。当前 read 返回 hex 与 serial；投稿需要新增专用备份结果记录与调用接口，不能靠任意本地路径读文件。
设备序列号如用于排错应仅在必要时私有保存，不默认发布。
进入 DFU 后未必能取得飞控品牌、硬件版本或 BF target；连接正常固件时能读取的信息提前采集，无法读取的字段由用户补填，界面区分读取值与人工填写值。

## 组件分工（建议）

| 组件              | 内容                                                                                                  |
| ----------------- | ----------------------------------------------------------------------------------------------------- |
| 软件投稿界面      | 选择本软件生成的备份、填写型号与版本、两张实拍图、公开分享确认、提交回执                              |
| 独立 Worker       | 投稿凭证、限额、文件校验、GitHub 写入、管理员登录、审核发布和下架接口                                 |
| D1 元数据库       | 建议保存投稿 ID、状态、对象索引、配额、审核记录及发布任务；不保存 HEX 和照片                          |
| GitHub 私有待审库 | 保存待审 HEX 与照片；建议使用私有仓库 Release 附件暂存，便于过期删除，避免每次拒绝都留下 Git 文件历史 |
| GitHub 公开备份库 | 第一版沿用 HEX 与照片分目录要求；软件读取 approved/index.json，不扫描全仓库                           |
| 电脑审核网页      | 查看材料、比对信息、通过/拒绝/下架、填写理由、查看失败任务                                            |

D1 是本轮提出的元数据实现建议，尚未创建；也可用其他可持久化的事务存储，但不应把状态仅留在 Worker 内存。GitHub 不是无限容量的投稿存储。上线时设总体预算和单条限额，增长后再评估把已发布大文件迁至 Release 附件；若迁移，先更新分目录需求和兼容清单。

## 投稿规则

1. 第一版从软件完整 Flash 备份结果发起投稿；单纯隐藏“任意文件上传”不能证明来源，服务端仍校验每一个请求。
2. 品牌、型号、硬件修订、MCU 型号、Flash 容量、BF 版本/target（能读取时）、备注，未知值如实标未知。
3. 两张用户本人提供的实拍照片为必填：手持飞控正反面，并有连接地面站的画面；现有照片只用于拍摄参考。
4. 服务器限制 HEX 字节大小、总解码大小、记录数量、照片类型/大小/像素、并发和每日投稿量。具体数值需按实际支持的 Flash 容量确定后写入统一配置。
5. HEX 检查记录校验和、合法记录类型、完整 EOF、地址上下界、重复或重叠地址、目标容量范围；完整备份地址范围按软件输出规则验证。格式通过不能证明固件与硬件兼容。
6. 分别计算 HEX 文件 SHA-256、解码 Flash 数据 SHA-256。客户端声明的哈希不是服务端校验结果。
7. 上传先申请短期单次凭证，校验声明大小和配额；失败/重试复用投稿 ID，避免重复创建仓库材料。未提交完或超时的材料定期清理。
8. 图片不接受 SVG/HTML；推荐客户端先缩图、重编码去除 EXIF，服务端核验文件内容和尺寸，不能只信扩展名或 Content-Type。图片元数据隐私处理需要明确测试。
9. 如保留免注册投稿，可配合 Turnstile、IP/会话配额和总容量闸门；IP 可变且多人共用，不能把限频称为完全防滥用。Turnstile 令牌须由服务端验证。
10. 固件不在服务器执行。两张照片和人工核对也无法保证每份固件可用或完全无恶意。

## 审核与发布

状态：uploading -> pending -> publishing -> published。可转 rejected、publish_failed、withdrawn；失败保留可追踪任务，不提前标为 published。

- 投稿进入 pending 后软件才提示“已提交，等待审核”，不能显示“上传成功即可下载”。
- 管理员使用 GitHub OAuth Web 登录；校验 state、回调地址、短期会话及服务端返回的固定用户 ID。写入权限凭据与登录凭据分离，客户端不带仓库写入 token。
- 审核网页展示两张大图、型号/硬件修订、读取与填写来源、两个哈希、HEX 结构检查结果和重复项提示。人工核实照片、板型和版本，必要时要求补充材料。
- 点击通过后，先写公开库 backups/<ID>/firmware.hex 和 images/<ID>/front.jpg、back.jpg，再校验上传结果，最后更新 approved/index.json。
- 同一备份发布过程保持幂等；清单修改处理 GitHub SHA 冲突，避免两位审核窗口同时操作丢条目。任何一步失败可重试，不重复发布或把半成品加入列表。
- 管理操作只接受指定管理员身份；所有批准、拒绝、下架接口均在服务端鉴权，不能只保护审核页面。
- 下架时先停止服务端列表与下载入口展示，并移除公开清单条目，再按管理需求删除文件；已缓存清单的客户端在刷新后同步，不宣称所有离线副本即时消失。
- GitHub 已公开直链、克隆、缓存与下载副本不能由软件下架保证撤回。按已确认需求接受此边界。
- 待审与拒绝材料设置保留期限，清理失败可见。若用 Git 提交保存待审文件，仅删除当前文件不清除历史，故建议私有 Release 附件暂存。

## 下载与离线

- 在线列表仅由已批准清单生成，支持品牌/型号、MCU、硬件修订、固件版本等筛选。
- 下载前保留用户原定的强制 10 秒阅读提醒及实验性功能说明；这里是界面提醒，不声称 GitHub 公开直链也会被倒计时限制。
- 下载先保存，核对 HEX 文件 SHA-256 后允许本地打开；不自动烧录，按现有刷写流程再次核对适用硬件。
- 初次投稿、在线审核、获取新清单及新文件需要网络；本地生成备份、查看已保存文件继续离线可用。
- 可由 Worker 提供已批准文件下载入口及缓存，作为后续性能选项；只公开清单中条目，不实现任意 URL 代理。

## 免费计划实现注意

- Worker 的请求体、内存、CPU、GitHub API 频率及存储预算都需要测量，不能把“轻量”理解为无上限。
- 完整 HEX 解码、图片处理可能超出免费 Worker 单次 CPU 预算；不要直接把高成本整文件解析/图像转码放进一个免费请求后保证能运行。实现前拿实际最大备份测 CPU，必要时分块校验、拆分任务或调整执行环境。
- 待审区和公开 Git 仓库都设置总容量监控；拒绝或清理请求不会天然回收 Git 历史空间。
- 上传受限时应明确提示暂不可投稿；下载和离线备份保持可用。公共清单缓存与分页减少 GitHub API 请求。

## 实施顺序

1. 在本地做三段连贯交互预览：软件投稿 -> 模拟待审 -> 电脑审核 -> 公开下载列表；明确标为演示，演示文件不可当作可烧录固件。
2. 后端实现与本地验证：校验、状态机、登录授权、重复请求/并发审核、发布中断、下架、过期清理；使用测试仓库材料，不提交真实固件。
3. 准备两个专用 GitHub 仓库、绑定管理员固定 ID、创建独立 Worker 及元数据库，再连接真实账号验证。账号资源与发布操作在明确授权后执行。
4. 通过验证后再接入地面站正式源码。安装包仅在用户明确要求打包时生成。
